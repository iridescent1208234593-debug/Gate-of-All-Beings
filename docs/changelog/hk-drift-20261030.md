## 本快照与线上仍存在的差异

`infra/ingress/zszm.conf.snapshot` 与线上 `/etc/nginx/conf.d/zszm.conf` 比对（22 插入 / 6 删除）显示，快照还缺线上已经生效的 `.xyz → .cn` 域名迁移，即：

- `map $host $qc_cn_target { … }` 整块
- `if ($qc_cn_target != "") { return 301 https://$qc_cn_target$request_uri; }`
- 扩展后的 27 条 `server_name`（含 `.cn` / `.dpdns.org` 三根域）

本 PR 只修恢复页这个具体缺陷，不含域名迁移同步；同步需要单独一个 PR，因为它改变的是入口路由语义而不是资源路径。

## 2026-10-30 追加：`.xyz→.cn` 迁移打断了 POST

| 线上改动 | 线上文件 | 状态 | 说明 |
| --- | --- | --- | --- |
| 旧域名页面保存/上传永久失败 | `/etc/nginx/conf.d/zszm.conf`（新增 `map $uri $qc_skip_cn` + 三段顺序 `if`） | **已修，本 PR 同步快照** | 原有的 `if ($qc_cn_target != "") { return 301 … }` 对所有 HTTP 方法生效。浏览器对 301/302 会把 POST 改成 GET 并丢弃请求体，因此停留在 `.xyz` 页面（迁移前打开且未刷新的标签页，或内嵌浏览器恢复的旧页面）的用户，`POST /api/images/upload` 与 `POST /api/save-character` 一律被 301 打断，前端 `fetch` 抛 `TypeError`，正好落到那句"暂时连接不上会馆保存服务，请检查网络后重试"。 |

证据：

- 实测 `.xyz` 上 `POST /api/save-character` 返回 `301 → https://huiguan.iridescently.cn/api/save-character`；同样请求在 `.cn` 上返回 `401`（说明接口本身正常）
- 访问日志里今天所有方法为 POST 却被 301 的记录：`/api/progress/report` ×3、`/api/images/upload` ×3、`/api/save-character` ×1，其中 `20:26:27` 的 upload 与 save-character 与用户反馈时间吻合
- 对照：当天 POST 累计 28607 次 200，只有个位数走错域，属边缘路径而非服务故障

修法与验证：

- `map $uri $qc_skip_cn { default 0; ~^/api/ 1; ~^/app/ 1; }`，再 `set $qc_redirect_cn 0;` 初始化，`if ($qc_cn_target != "")` 置 1、`if ($qc_skip_cn = 1)` 置 0，最后 `if ($qc_redirect_cn = 1) return 301`
- reload 后实测：`.xyz` 页面 `GET /` 仍 301 到 `.cn`；`.xyz` 上 `POST /api/save-character` → 401、`POST /api/images/upload` → 400、`GET /api/sso-user` → 200；`zszm.iridescently.xyz` 的 `/app/modules/cards/`、`/app/shell/` 由 301 变 200；`.cn` 四站首页与 API 状态与改前一致
- 首次 patch 漏了 `set $qc_redirect_cn 0;`，nginx 对非 `.xyz` 宿主每请求刷 `using uninitialized "qc_redirect_cn" variable` 告警；补上初始化后 reload，新告警 0 条
- 备份：`zszm.conf.bak-cnredirect-20261030-202813`、`zszm.conf.bak-cnredirect-init-20261030-202834`
