# AI 开发统一规则

本文件规定 Claude、Codex、Copilot 及其他代码生成工具在本仓库中的共同工作方式。它不是某个模型的专属提示词；项目事实必须留在仓库，单次 Prompt 只描述“这一次做什么”。

## 1. 规则优先级

开始任何改动前，按以下顺序读取并服从：

1. 根目录 `AGENTS.md`：仓库级安全与操作边界。
2. 与任务直接相关的现行架构/数据/安全文档。
3. `docs/development/GLOSSARY.md`：核心术语及语义。
4. `docs/development/NAMING_AND_CONTRACTS.md`：变量、字段、API 与环境变量命名规则。
5. `.github/instructions/` 下与改动路径匹配的规则。
6. 相关源码、测试和当前接口实现。

文档与源码冲突时，不允许自行猜测“正确版本”。先以当前源码和测试确认真实行为，并在 PR 中记录冲突；涉及生产状态时遵守 `AGENTS.md` 的实时证据要求。

## 2. AI 开工前必须做的事

AI 在写代码前必须先完成以下检查：

- 确认当前分支、目标分支和任务允许修改的路径。
- 搜索现有实现、类型、Schema、API、数据库字段与测试，优先复用既有概念。
- 检查是否已经存在同义变量、共享类型、配置或工具函数。
- 明确哪些是公共契约，哪些只是模块内部实现。
- 明确是否涉及数据迁移、兼容旧客户端、旧存档或外部调用方。

禁止仅凭 Prompt 中的一段自然语言重新设计已有架构。

## 3. 禁止 AI 自行创造平行概念

下列内容视为“核心契约”：

- 身份、账户、owner、玩家形象、OC、存档、scope 等领域概念；
- 跨模块共享字段和类型；
- API 请求/响应字段；
- 数据库表、列、索引与唯一性约束；
- 环境变量；
- URL/Host/Origin/会话边界；
- Release、runtime storage、production 等运维概念。

如果现有概念可以表达需求，必须复用，不得再造同义词。例如已经存在 `user_id` 时，不得仅因个人偏好新增 `userIdString`、`accountId`、`member_id` 来表达同一个语义。

如果确实需要新增核心概念，必须在同一 PR 中：

1. 说明旧概念为什么不能表达；
2. 更新 `GLOSSARY.md`；
3. 更新 `NAMING_AND_CONTRACTS.md` 或对应 API/数据文档；
4. 为兼容/迁移补测试；
5. 若改变架构边界，再补 ADR 或等价设计记录。

## 4. 不允许“顺手重命名”公共契约

仓库当前存在历史兼容字段，例如 `uid`、`user_id`、部分模块的 `player_id`。这些名称可能对应不同层或不同历史接口。

因此：

- 不得做未经授权的全局搜索替换；
- 不得把数据库列、外部 API 字段和内部变量当成同一层处理；
- 重命名公共字段必须有兼容窗口或明确迁移；
- 新代码应在边界层归一化，再在内部使用统一语义；
- 旧名称只有在调用方、数据和测试均完成迁移后才能删除。

详见 `NAMING_AND_CONTRACTS.md`。

## 5. 单次 AI 任务 Prompt 只写任务，不复制项目百科

推荐使用 `docs/development/AI_TASK_TEMPLATE.md`。每次至少给出：

- 目标；
- 允许修改范围；
- 明确禁止范围；
- 必须保持的兼容性；
- 验收条件；
- 需要运行的测试/构建。

不要为每个开发者维护一份彼此不同的“众生之门超级提示词”。项目知识写进仓库文档，Prompt 只引用这些文档。

## 6. AI 修改原则

- 优先最小改动，不为“更优雅”扩大任务范围。
- 优先使用 `packages/*` 中已有共享能力；不要复制一套新的 auth/session/data/UI contract。
- 不把源码目录当运行时数据目录。
- 不修改生产、Cloudflare、DNS、Tunnel、OAuth、真实数据库和用户上传，除非负责人明确授权。
- 不删除无法确认用途的数据、素材、原件、日志、备份或凭据。
- 不把测试跑不了写成“通过”；必须记录实际命令和实际结果。
- 不凭猜测补值。信息不足时把未知项写入 PR 风险/待确认项。

## 7. AI 完工后的交付格式

AI 的 handoff 至少包含：

- 修改了哪些文件；
- 行为变化是什么；
- 是否改变公共契约；
- 是否新增术语/字段/API/环境变量；
- 兼容和迁移如何处理；
- 实际运行的测试及结果；
- 未验证项与剩余风险。

只有文档改动也应说明“未运行代码测试”的原因，不要伪造验证结果。
