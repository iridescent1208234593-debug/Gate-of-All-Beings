# 12 · 端到端联调记录（R8）

> 本文档记录 R8 轮次的**端到端联调链路**：对战内核 → 战斗日志契约 → 成就判定 → 收集图鉴，
> 补齐 R5/R7 遗留的「端到端联调产物待补」三项，并对镜像战不计入角色收藏做回归。
> 定位：`docs/03-对战系统.md`（内核） + `docs/04-成就系统.md`（判定与图鉴） → 本文档（**链路联调与验证据**）。
> 数据源：`data/generated/character_stats.json`（488 名，model 1.1.0）、`data/decks.json`（488 套）、
> `data/achievements.json`（15 条，v1.1.0 / R7）；全部为派生值，**保留 `source` / `confidence` 溯源标记，不称官方权威值**。

---

## 1. 触发

R5 与 R7 两轮的未决项中均挂账一项：

> 端到端联调产物待补（`toLogRecord` 落盘样例 / 成就判定全 15 条覆盖 / 图鉴四视图渲染自检）

此前 `data/scripts/smoke_test.js` 已覆盖内核、克制环、镜像战、成就抽样与图鉴**长度**断言，
但缺少：① 战斗日志**落盘样例**；② **全 15 条**成就的逐条达成验证；③ 图鉴四视图的**渲染自检**（非仅长度）。
R8 以独立脚本 `data/scripts/e2e_flow.js` 补齐三项，并接入 `scripts/run_all.ps1` 作为第 7 步。

---

## 2. 链路与命令

```powershell
# 单独运行（只读 data/ + ui/，只写 data/generated/e2e/）
node "data\scripts\e2e_flow.js"

# 并入一键链路（数值 → 卡组 → 校验 → 审计 → JS 自检 → 冒烟 → 端到端联调）
powershell -ExecutionPolicy Bypass -File "scripts\run_all.ps1"
```

**退出码**：`0` = 15/15 成就达成且各项自检通过；`1` = 存在失败项。

**链路阶段**：阶段0 基础对局取证 → 阶段1 主线 30 连战 → 阶段2 越档挑战 → 阶段3 镜像战 →
阶段4 六系取证 → 阶段5 零损血取证 → 解锁阶梯 1 / 30 / 100 / 488 名。

## 3. 三项待补的落地结果

### 3.1 战斗日志契约落盘样例 ✅

- 契约字段（顺序即契约顺序，`docs/04 §5`）：`battle_id, mode, my_character_id, opponent_id, opponent_type, result, turn_used, hp_left, hp_max, seed`
- 样例文件：`data/generated/e2e/battle-log-sample.jsonl`（**8 条**，JSONL，每行一条完整契约记录）
- 脚本内断言：`toLogRecord` 输出字段与顺序**逐字比对契约数组**；常规对局 `turn_used ≤ TURN_LIMIT(30)`

### 3.2 全 15 条成就逐条覆盖 ✅

| 类别 | 条数 | 达成 | 首次触发阶段 |
| --- | --- | --- | --- |
| 角色（character） | 4 | 4 | `ach_character_001` → 阶段1；`_030` → 阶梯 30；`_100` → 阶梯 100；`_488` → 阶梯 488 |
| 六系（system） | 3 | 3 | 全部 → 阶段4 六系取证 |
| 战斗（battle） | 4 | 4 | `_001` → 阶段1；`_002` → 阶段2；`_003` → 阶段3；`_004` → 阶段4 |
| 稀有度（rarity） | 4 | 4 | `UR` → 阶段1；`SSR` → 阶梯 30；`SR` → 阶梯 100；`R` → 阶梯 488 |

- 判定口径：由 `ui/achievement-system.js` 的 `judge(log)` 读**战斗日志契约字段**驱动，败局自动跳过
- **真实对局优先**：本轮 106 场对局**全部为真实内核对局**（`real = 106` / `synthetic = 0`），
  未使用任何契约级合成记录；脚本仍保留 `judgeSynthetic()` 通道（合成记录会落盘并显式标注 `trigger = synthetic`），本轮**零调用**
- 成就快照：每个阶段前取 `unlocked_achievement_ids` 快照，阶段后比对得出「本阶段新解锁」，写入报告的 `stages` 数组

### 3.3 图鉴四视图渲染自检 ✅

`codex()` 四视图逐项自检（`labels_ok` / `pct_ok` / 组内条目数 = 组 owned = 全库 488）：

| 视图 | 分组数 | 组内条目合计 | 自检 |
| --- | --- | --- | --- |
| 六系图鉴 by_element | 7（金33 / 木27 / 水26 / 火16 / 土7 / 空间7 / 无系372） | 488 | PASS |
| 稀有度图鉴 by_rarity | 4（R413 / SR71 / SSR3 / UR1） | 488 | PASS |
| 分档图鉴 by_tier | 6（F339 / E74 / D55 / C16 / B3 / A1） | 488 | PASS |
| 主线名录 by_mainline | 2（主线30 / 非主线458） | 488 | PASS |

> 自检不仅断言分组数量，还校验每组 `label` 非空、`pct` 与 owned/total 一致、组的 `owned` 合计等于全库总量。
> 土系 7 名与 R7 修正结论一致（含池年 · C 档）。

### 3.4 镜像战不计入收藏回归 ✅

- 口径：`opponent_type = mirror` 的胜利**不计入**角色胜利收藏（`unlocked_characters`）
- 回归方式：记录镜像战胜负前后的 `mainline_defeated` 与 `unlocked_characters`，比对增量
- 结果：`defeated_after_official = 1` / `defeated_after_mirror = 1`（**镜像胜未产生额外收藏**），`pass = true`
- 同时覆盖 `ach_battle_003`（镜中人 · `mirror_wins` 3 胜）本身仍需计数，二者语义不冲突

## 6. 局限与未决

1. 本链路为**内核级**联调（Node 环境直调模块），不含浏览器渲染层；UI 组件的 DOM 级验证仍属站点侧 P7 挂载后的工作。
2. 平衡性仅做「能否取胜」的可行性探测（有限种子），**未做胜率统计**（P5 的 45%~55% 胜率目标仍需站点实测样本回归）。
3. `ach_battle_001` 依赖自身对战补齐的路径已在 §4 记为 R9 议题，本轮不改判。
4. 站点侧挂载与表情包专项采集仍为未决项（见 `CHANGELOG.md` R8 一节）。
